## Implementation and reused engine

A separate opt-in command-line executable, careercompiler-migrate012, now wraps the existing native Migration 012 runner. It does not launch Tauri windows or initialize the application repository. It is built only when the migration012-adapter Cargo feature is explicitly selected. Normal builds exclude that executable; the original career_compiler binary remains the default run target.

The backup/transaction/rebuild/recovery implementation is byte-for-byte unchanged from the preserved baseline (engine-reuse-and-boundaries.json). No second migration engine was created. The existing fixture loader moved from tests.rs to fixture.rs so the CLI and tests create the same deliberate synthetic records. The reviewed SQL is unchanged; SHA-256 cbaab894011a6cd889388b9b28bebd9b9714df70109caa0e723048b0bd229d14.

The adapter:
1. Requires strict arguments, an absolute target database path, an absolute invocation manifest, its exact SHA-256, and confirmation MIGRATE_011_TO_012.
2. Rejects missing, duplicate, unknown or malformed arguments; no force/skip-preflight flag exists.
3. Rejects owner mode with migration012_ProductionExecutionDisabled before any target/manifest filesystem access. No environment variable or runtime setting enables it.
4. Synthetic mode accepts only the canonical root generated by prepare-synthetic under the dedicated temporary directory, its fixed synthetic.sqlite3 filename, its OWNER marker, and a matching bounded manifest. Unknown fields, changed hashes, links, file identities and scopes fail closed.
5. Pins source database/sidecar device/inode/content and a logical data fingerprint. After opening the one native SQLite connection and obtaining exclusive SQLite ownership, it rechecks logical state before calling the existing runner.
6. The runner validates exact 011 schema/history/metadata, integrity and foreign keys, creates and reopens a fresh WAL-safe backup, executes the reviewed rebuild transaction, atomically records ID 12, verifies all original values, restores foreign keys, and reopens/validates.
7. Closes its owned connection and produces a receipt referencing the verified backup. Errors expose fixed codes, not private SQL or row contents.

The manifest is an invocation binding for deliberately created fixtures, not an authentication credential or a general license to access arbitrary files. The adapter has no production path resolver, Keychain access, startup hook, or Tauri handler. Acceptance guards, production identifier, Tauri permissions, existing transaction allowlists and automatic migration registration are unchanged. Normal startup still registers migrations only through 011.

## Commands and eventual invocation contract

Build the isolated maintenance executable:

    cargo build --manifest-path src-tauri/Cargo.toml --locked --offline --features migration012-adapter --bin careercompiler-migrate012

Create a deliberate fixture (returns database, manifest and manifestSha256):

    careercompiler-migrate012 prepare-synthetic --fixture representative

Use fresh instead of representative for an empty synthetic installation. Creation accepts no existing database path.

Execute only the returned synthetic target:

    careercompiler-migrate012 migrate --mode synthetic --database ABSOLUTE_RETURNED_DATABASE --manifest ABSOLUTE_RETURNED_MANIFEST --manifest-sha256 RETURNED_SHA256 --confirm MIGRATE_011_TO_012

The intended owner invocation shape uses --mode owner and separately reviewed target/manifest values. **That mode unconditionally fails in this build. It is not an executable real-data migration instruction.** Neither a synthetic manifest nor changing the mode flag can authorize real data.

The owner-target opening branch is implemented: it accepts only a private OwnerPermit binding the exact target path, separate recovery root and invocation-manifest SHA-256, then performs the same identity, exclusivity and runner checks. Its migration and quarantine/restore behavior were tested using only freshly created synthetic targets and a separate synthetic recovery directory. Mismatched target and manifest grants are rejected before opening the target.

The public owner_authorization policy currently returns ProductionExecutionDisabled unconditionally. A caller cannot construct OwnerPermit through the public API, supply it via a flag, or enable it with an environment variable. Only tests privately issue a capability for deliberate synthetic fixtures.

Separate owner authorization is required to pin and issue the real-target permit and its current reviewed manifest. This is an authorization-policy change; the target-opening path and migration engine are already implemented and tested. The synthetic path restrictions must not be removed to activate owner mode.

## Preflight, backup and recovery safeguards

The engine compares the complete native SQLite schema through 011: tables, declarations, defaults, constraints, indexes, triggers, views, dependencies and known optional FTS schema. It explicitly checks all 22 résumé columns/four explicit indexes, exact migration IDs/names, nonempty applied timestamps, expected database metadata and all references. Unknown or incompatible inputs stop without repair.

One SqliteConnection retains SQLite exclusive locking across preflight, backup and transaction. VACUUM main INTO produces a consistent logical snapshot including committed WAL content; the new backup is synced, reopened, checked for integrity/FKs, hashed and compared against every source table fingerprint before the rebuild. A previous backup is not silently reused. No schema modification occurs without this backup.

Foreign keys are disabled before BEGIN IMMEDIATE, the exact reviewed rebuild runs, every original table value is compared before history/audit insertion, and ID 12 is recorded atomically. Foreign keys are restored and verified. Reopen checks schema, history, fingerprints and referential integrity again.

Injected pre-commit failures roll back the original schema/data/history. Real owned child-process interruptions after DROP and history insertion reopen as 011 with no partial 012. A post-commit validation failure uses the existing verified-backup restore and retains the migrated database/sidecars in quarantine. Failed recovery reports RecoveryRequired instead of silently retrying.

A successful adapter request becomes stale because its pinned source snapshot changes. Repeating it returns StaleInput without a second migration, backup or history row. The underlying engine's existing validated AlreadyApplied no-op test also passes. Recovery invalidates old inode bindings; do not retry a restored database with an old manifest.
